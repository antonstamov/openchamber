# Обратный прокси

Используйте эту страницу, если запускаете OpenChamber за Nginx, Nginx Proxy Manager, Caddy, Cloudflare или другим обратным прокси.

## Прежде чем проксировать

1. Сначала убедитесь, что OpenChamber работает напрямую.
2. Откройте `http://<server-ip>:3000` или ваш пользовательский порт из той же сети.
3. Добавляйте обратный прокси только после того, как прямое подключение заработало.

## Что должен поддерживать прокси

- WebSocket для живого транспорта сообщений:
  - `/api/event/ws`
  - `/api/global/event/ws`
  - `/api/terminal/ws`
- SSE без буферизации:
  - `/api/event`
  - `/api/global/event`
  - `/api/notifications/stream`
  - `/api/openchamber/events`
  - `/api/terminal/:sessionId/stream`
- Большие тела запросов для вложений и файловых операций
- Длинные таймауты чтения для живых потоков и терминальных сессий

## Важные правила

- Включите проксирование WebSocket.
- Отключите буферизацию на SSE-маршрутах.
- Отключите gzip на прокси, если OpenChamber уже сжимает ответы.
- Держите сжатие включённым только в одном месте.
- Пробрасывайте обычные прокси-заголовки, такие как `Host`, `X-Forwarded-For` и `X-Forwarded-Proto`.
- Увеличьте лимиты размера тела, если пользователи загружают файлы.

## Быстрый чек-лист

- OpenChamber доступен напрямую по LAN
- WebSocket включён в прокси
- На SSE-маршрутах отключена буферизация
- `gzip off` на хосте прокси, либо сжатие прокси отключено иначе
- `client_max_body_size` достаточно велик для вложений
- `proxy_read_timeout` достаточно длинен для потоков

## Типичные признаки проблем

### Страница загружается, но отправка сообщений не работает

- WebSocket не включён в прокси
- `/api/event/ws` или `/api/global/event/ws` проксируется некорректно

### Уведомления или живой статус не обновляются

- один из SSE-маршрутов буферизуется или кэшируется
- отсутствует `X-Accel-Buffering "no"`

### Загрузка файлов не работает

- `client_max_body_size` слишком мал

### Всё работает локально, но ломается только за прокси

- прокси сжимает и буферизует живой трафик
- в прокси нет поддержки WebSocket

## Пример: Caddy

<details>
<summary>Show example config</summary>

```caddy
reverse_proxy 127.0.0.1:3000 {
    # WebSocket support is automatic in Caddy

    # Flush SSE responses immediately
    flush_interval -1

    # Pass through Host and proxy headers
    header_up Host {host}
    header_up X-Real-IP {remote_host}
    header_up X-Forwarded-For {remote_host}
    header_up X-Forwarded-Proto {scheme}

    # Increase timeouts for long-lived streams
    transport http {
        read_timeout 3600s
        write_timeout 3600s
    }
}
```

</details>

Caddy обрабатывает апгрейд WebSocket автоматически — дополнительная настройка не нужна. Директива `flush_interval -1` заставляет немедленно отправлять чанки SSE без буферизации.

## Прокси входа (Authentik, Authelia, oauth2-proxy)

Если пользователи входят на прокси до того, как попасть в OpenChamber, панелям расширений нужно одно исключение. Панель работает в изолированном фрейме, и браузер не отправляет sign-in cookie прокси с собственными запросами этого фрейма, поэтому прокси отдаёт файлам панели свою страницу входа, и панель остаётся пустой.

Разрешите `/api/guest-files/` без входа. Этот путь отдаёт только файлы установленных расширений и только по ссылке, которую OpenChamber выдаёт вошедшему пользователю для этой панели. Больше он ничего не открывает. С Nginx и `auth_request`:

```nginx
location ^~ /api/guest-files/ {
    auth_request off;
    proxy_pass http://127.0.0.1:3000;
}
```

В других прокси добавьте правило, пропускающее вход для того же префикса пути. Не освобождайте `/api/guests/`: этот путь также устанавливает расширения и обслуживает их запросы, и без пароля интерфейса OpenChamber им мог бы пользоваться кто угодно.

## Предупреждение о CDN и двойном сжатии

Если перед обратным прокси стоит CDN (например Cloudflare), остерегайтесь двойного сжатия:

- OpenChamber сжимает HTTP-ответы gzip (порог 1 КБ).
- Cloudflare и другие CDN также сжимают ответы по умолчанию.
- Это может приводить к дважды сжатым ответам или неверным заголовкам `Content-Encoding`.

Чтобы этого избежать, отключите сжатие на **одном** уровне:

- **Cloudflare:** Rules → Compression — отключить (или режим «Passthrough»).
- **Nginx:** `gzip off` (уже показано в примерах выше).
- **Caddy:** Caddy по умолчанию не пересжимает, если апстрим уже прислал сжатое содержимое.

Маршруты потокового SSE OpenChamber исключает из сжатия, но CDN всё равно может их буферизовать. Как отключить буферизацию SSE-путей, смотрите в документации вашего CDN.
